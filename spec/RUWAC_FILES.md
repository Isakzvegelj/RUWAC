# Native SSH files

Open an SSH machine to create its persistent terminal and in-window Files view. RDP-only machines do not imply an SSH service. Existing SFTP upload/download, verified host keys, Secret Service passwords/encrypted-key references and retained pause/resume journals remain available.

The Files view also offers rsync upload of a file or folder, and download of a selected remote item into a chosen local directory. Select chooses a row without navigating; clicking its directory name opens it. Enter one remote item name before transferring. Rsync requires both endpoints to provide version 3.4 or newer and an SSH key or unlocked agent. Password-only or locked-key connections can use SFTP. Install the Fedora `rsync` and `openssh-clients` packages when needed. No password is placed in argv, environment, clipboard, logs or automation replies.

Rsync detection uses an authenticated fixed remote command. Known-host checking is strict against the same selected trust file, global fallback/config hooks are disabled and UpdateHostKeys is explicitly off. Gateway metadata does not silently become a direct rsync connection: a nonempty unsupported gateway is refused. Paths are separate argv values; no user path enters a `sh -c` command. The NUL-delimited explicit file list preserves spaces, quotes, Unicode, wildcard characters and shell metacharacters as literal names. Source trees reject symlinks, devices and special files.

Each copy goes into an owned private staging directory. The complete regular-file set, byte sizes and SHA-256 values are checked before publication. Basic permission bits and modification times are preserved, without ownership, special permission bits, ACLs or extended attributes. This is a verified staged copy, not a filesystem snapshot of a concurrently changing source. Bounds are 32 GiB total, 10,000 entries, 64 directory levels and 4 KiB paths. UTF-8 paths are required. Hash scans and transport phases have cancellation and time limits; rsync allocations are capped.

Existing destinations are refused by default. The separate rsync replacement checkbox replaces the entire destination, including files absent from the source; it does not merge directories. A verified copy is committed with no-replace rename. Explicit replacement first retains the original as an owned backup, restores it if commit fails, then removes the backup after success. A competing actor or cleanup failure can leave a named backup/staging path for inspection. Portable SFTP does not provide a directory transaction spanning every remote actor or power failure.

Pause transfer pauses SFTP with its existing journal; for rsync it cancels the owned process group, removes owned staging and preserves the destination until commit. Rsync cancellation starts a new copy on retry and does not reuse the SFTP resume journal. New copies create private durable recovery records before staging. Interrupted rsync copies opens the endpoint’s records. Recover restores a verified original when its destination is missing, or retains a verified published replacement, then cleans only marked staging and verified backups. Changed destinations, backups, markers, profiles or host identities are refused for inspection. Live copies retain locks, and cooperating new rsync publish/recovery mutations serialize. Recovery does not blindly resume data transfer or overwrite an unexpected destination. Unmarked staging from an interruption before its ownership marker is retained for manual inspection. Remote power-loss and all independent-actor race windows remain separate qualification gates.

The [upstream rsync manual](https://download.samba.org/pub/rsync/rsync.1) documents secluded arguments, literal file lists, progress and remote-shell parsing. RUWAC uses the established OpenSSH/rsync implementation and its existing SFTP verification adapter; the headless daemon remains independent of these desktop file operations.

Existing destinations require explicit whole-destination replacement; no merge or source deletion is implied. ## Interrupted rsync recovery — compiled package 0.2.4

The Files view adds Interrupted rsync copies with explicit Recover actions. Private, atomically written and synced recovery metadata records endpoint/configuration binding, original SSH fingerprint, owned staging/backup paths and content/tree digests. Per-job locks prevent concurrent recovery of a live job. Cooperating new rsync publish/recovery mutations serialize. Recovery validates markers, root identity/mode/owner/time and complete file contents before restoring a missing original or retaining a verified published replacement. Unexpected destinations, changed backups/markers/profiles, malformed records or replacement SSH hosts are refused without deleting the retained data. Local-only rollback checks captured endpoint settings and local identity without requiring the remote host online; remote mutation requires the original verified host key.

Normal publication now rechecks originals and backups before commit/cleanup, reports observed recovery outcomes explicitly and retains ambiguous records for inspection. Local rename directories and recovery metadata are synced; rsync uses file sync, and remote ownership markers require the server's sync extension. This is client-process interruption recovery, not an unconditional remote power-loss guarantee. Partial transfers restart; unmarked staging from the creation/marker gap is retained for manual inspection. Previous unmarked copies are not adopted blindly. SFTP's existing resume jobs remain unchanged.

Six actual loopback SSH/rsync groups pass: 20 SIGKILL transitions across upload/download and files/directories; an actual in-flight rsync child crash; stale profile/tampered marker/staging mode/destination/journal refusal; normal resumed commit refusal after independent backup/destination edits; actual SSH rekey with updated trust still refusing retargeted recovery; and real native recovery-dialog callbacks restoring an original while preserving terminal PID. The native chooser/callback runs synthetically on an isolated compositor, not a physical seat. Eight independent actual authorized Fedora-host SIGKILL/recovery cases pass upload/download of files/directories at backup-moved and published boundaries, with independently checked hashes, unchanged owner SSH files and removal of generated remote fixtures. No remote service reboot or owner clipboard/keyring mutation occurs.
